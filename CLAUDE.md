# ggege — образовательное приложение (ЕГЭ-подготовка для школьников)

Duolingo-style приложение: Next.js 14 (App Router) + Drizzle ORM (postgres-js)
+ Tailwind + Framer Motion + lottie-react + Zustand + react-latex-next/KaTeX.
Курсы: ЕГЭ Математика Профиль (courseId=11), ЕГЭ Физика (courseId=12),
ЛНИП Физика 7 (courseId=10) и другие.

## ⚠️ Критическое ограничение: изоляция от asfalt-app

На той же VPS (168.222.192.167) крутится **совершенно не связанный** проект
"asfalt-app" под pm2-процессом `asfalt-app`. Это чужой проект, не имеющий
отношения к ggege. **Никогда не перезапускать, не останавливать и не
трогать `asfalt-app`** ни при каком деплое или отладке ggege.

Перед любым `pm2 restart`/деплоем — снять `pm2 list` и запомнить
uptime/restart-count у `asfalt-app`, после деплоя — сверить, что они не
изменились. Перезапускать только сам `ggege` (и, если нужно,

## Деплой

```bash
git add <файлы> && git commit -m "..." && git push origin main
ssh root@168.222.192.167 "cd /var/www/ggege && git pull origin main && npm run build && pm2 restart ggege"
```

Если менялись только данные в БД (seed/update-скрипт), а не код приложения —
деплой (build+restart) **не требуется**: `DATABASE_URL` в `.env` указывает
на ту же продовую БД, что видит и прод-сервер, так что `npx tsx scripts/...`
локально уже пишет в прод.

Со статикой из `public/` (SVG-диаграммы и т.п.) тоньше: **изменение
содержимого уже существующего** файла подхватывается сразу после `git
pull`, без build/restart (Next.js standalone раздаёт его по тому же inode).
А вот **новый** файл, которого не было в прошлом билде — 404, пока не
сделать `npm run build` (копирует `public/` в `.next/standalone`) —
проверять `curl -s -o /dev/null -w '%{http_code}' http://localhost:3001/...`
до вывода "деплой не нужен".

## Наполнение курсов задачами (sdamgia.ru)

Курсы пополняются задачами, спарсенными с `phys-ege.sdamgia.ru` /
`math-ege.sdamgia.ru`. Основной паттерн — один seed-скрипт на юнит/урок,
см. `scripts/seedEGEPhysics-unit*-lesson*.ts` как образец (структура:
создать unit/lesson → на каждую задачу `insert challenges` → `insert
challengeOptions` с перемешанными вариантами). Пример скрапинга:
`scripts/scrape-sdamgia.ts`.

### Как достаётся условие задачи

Постранично: `test?theme=<ID>&sort=ids&page=N` (5 задач/страница,
`sort=ids` = по убыванию id = от новых к старым) — так собирается полный
список id темы. Дальше на каждую `problem?id=<ID>` вытаскивается:

- условие — `<div id="body...N" class="pbody">...</div></div><!--np-->`
- иллюстрация (если есть) — `<img src="/get_file?id=X">` внутри pbody
- готовые варианты ответа ("Тип 2", когда они у sdamgia реально есть) —
  спрятаны в HTML-комментарии рядом с текстом `generated from answers`.
  **Место разрыва этого маркера внутри комментария у sdamgia плавает**
  (`<!--auto ge...nerated from answers-->` в одной задаче,
  `<!--auto generated...from answers-->` в другой) — не завязывайтесь на
  точный текст маркера, ищите весь `<!--auto.*?-->` целиком и разбирайте
  варианты внутри по разделителю `N)&#8239;&#8239;...`
- решение (полезно для придумывания дистракторов, см. ниже) —
  `<div id="sol<ID>" class="solution">...`
- правильный ответ — скрытый `<div class="answer">Ответ: X</div>`
  (надёжнее, чем видимый "Ответ:" внутри текста решения)

### Конвертация формул в LaTeX

`<img class="tex" alt="...">` в тексте условия — alt это **словесное**
описание формулы для скринридеров ("дробь: числитель: X, знаменатель: Y
конец дроби" = X/Y, "в квадрате" = ², "корень из: начало аргумента: ...
конец аргумента" = √...), а не готовый LaTeX. Конвертируется вручную по
смыслу (или через Claude) в `$...$`.

**Важно про подстрочные индексы:** многобуквенный/кириллический подстрочный
индекс обязательно оборачивать в фигурные скобки — `$F_{тр}$`, `$E_{к}$`,
не `$F_тр$`/`$E_к$` (последнее в KaTeX/react-latex-next рендерится только
с ПЕРВОЙ буквой индекса как подстрочной, остальное — обычным текстом; была
найдена и исправлена задним числом в одном уроке, проверяйте на новых
задачах).

Символы-артефакты HTML: `&#8239;` (узкий неразрывный пробел) → обычный
пробел, `&#8288;` (word joiner) → убрать, мягкие переносы (`\xad` /
"мас­сой") → убрать.

### Таблицы данных в условии

Если в `pbody` встречается `<table>` — sdamgia просто рисует HTML-таблицу.
`question` в БД — это **plain text + `$...$` для KaTeX**, полноценный HTML
не поддерживается компонентом вопроса (`app/lesson/question-bubble.tsx`,
рендерит через `<Latex>{question}</Latex>`). Поэтому таблица переносится в
условие **не как текст**, а как аккуратная SVG-картинка (см.
`scripts/svg-tools/render_table.py` — пример на теме 217, задача про
F(x) пружины), подключённая через `imageSrc`, как обычная иллюстрация.

### Диаграммы/графики к задаче

**Никогда не рисовать диаграмму "на глаз" по тексту условия.** Всегда:
1. Скачать оригинал `curl -s "https://phys-ege.sdamgia.ru/get_file?id=<ID>"`
2. Разобрать геометрию: серый `stroke` (обычно `#ADAAAA`) — сетка, чёрный
   (`#010202`/`#000000`) — оси/стены/земля, цветной (обычно `#CC761F`) —
   сама кривая/вектор данных. Текстовые подписи чисел на осях у sdamgia
   зашиты как глиф-пути внутри `<defs>/<clipPath>` — не парсить их текст
   напрямую, читать визуально (см. ниже) или ориентироваться по
   `<rect>`-якорям внутри `<defs>`.
3. **Визуально свериться с оригиналом** — открыть его в Browser pane
   (см. `mcp__Claude_Browser__preview_start`/`navigate`, оригинал можно
   отдать локальным `python3 -m http.server` из папки со скачанным SVG,
   т.к. `file://` рендерится только статичным снэпшотом) и прочитать
   реальные числа-подписи осей глазами, не угадывать.
4. Перерисовать в своей палитре, используя `scripts/svg-tools/*` как базу
   (см. `scripts/svg-tools/README.md`), сохранить в `public/geometry/`
   с именем вида `phys<тема>_<id задачи>.svg`, подключить через `imageSrc`.
5. Снова визуально сверить получившийся файл с оригиналом бок-о-бок
   (скриншот) прежде чем класть в БД/деплоить.

Частый баг при такой перерисовке — подписи делений оси обрезаются, если
`viewBox`/`height` канваса впритык под сами линии сетки, без запаса под
текст под/слева от последней линии. Всегда оставляйте явный отступ
(`MARGIN_L`/`BOTTOM_PAD` в `render_energy_graph.py` — обход этого бага).

### Правильный ответ — всегда доверенный, никогда не перепроверять

**Правильный ответ = поле "Ответ:" со страницы sdamgia, копируется
буквально.** Никогда не пересчитывать физику/математику задачи заново,
чтобы "проверить" ответ sdamgia, и тем более не подгонять диаграмму под
свои вычисления вместо оригинала. Единственное законное применение
собственных физических рассуждений — придумывание **неверных** вариантов
(дистракторов), см. ниже.

### Дистракторы (неверные варианты ответа)

**Начиная с Unit 7 lesson 3 (theme 393) — 5 дистракторов на задачу, то
есть 6 вариантов ответа всего** (раньше в разных юнитах курса "ЕГЭ
Физика" было вперемешку то 4, то 5, то 6 — несогласованно; курс "ЕГЭ
Математика" всегда использовал 6). Явная инструкция пользователя: во всех
новых уроках — 6 вариантов. Карточка задачи (`app/lesson/challenge.tsx`)
рендерит любое число вариантов без ограничений (grid без `slice()`), так
что технических препятствий нет.

Когда у задачи есть официальные варианты sdamgia ("Тип 2", см. выше) —
берём их как есть (даже если их не 6 — это чужие проверенные варианты, не
подгонять их число под правило выше).

Когда официальных вариантов нет — **дистракторы должны быть
индивидуально подобраны под физику конкретной задачи**, не одной формулой
на все задачи подряд. Была системная проблема: 241 из ~300 старых задач
курса "ЕГЭ Физика" использовали фиксированную формулу
`[correct-1, correct+1, correct*0.5, correct*1.5, correct*2]` — из-за
этого верный ответ был статистически угадываем (единственное число с
соседями ±1) без решения задачи. Это исправлено (`scripts/
fixDistractorsEGEPhysics.ts`), но при добавлении новых задач без
официальных вариантов — придумывайте под каждую конкретно правдоподобную
ошибку школьника (забыл ÷2/×2 в формуле, забыл возвести в квадрат, ошибка
знака, не перевёл единицы, перепутал соседний участок графика/данные из
условия и т.п.), варьируя тип ошибки от задачи к задаче. Решение sdamgia
(`<div class="solution">`) — хороший источник правдоподобных "промежуточных"
неверных значений, но использовать его можно только для этого — не для
проверки самого правильного ответа (см. выше).

### Баг тренажёра, найденный при проверке пилота (2026-08-27)

При живой проверке бейджа скила — реши урок 2103 правильно, бейдж
остался 0%. Причина не в бейдже (он честно читает БД), а в самом
тренажёре: `app/t-lesson/[t_lessonId]/TQUIZ.tsx`, `goToNextQuestion`
(мемоизированный `useCallback`) замыкал `score` по значению на момент
своего создания. `handleAnswer` вызывает `setScore(prev => prev+1)`,
затем (в той же самой async-функции, после `await sleep(400)`) —
`goToNextQuestion()`. React не подменяет замыкание уже запущенной
функции на лету, поэтому `goToNextQuestion` в этот момент видел ЕЩЁ
СТАРОЕ значение `score`, читая `score`/`questions.length - score` для
записи в `t_lesson_progress`. У типа `ASSIST` баг не проявляется (клик
на "далее" — отдельное взаимодействие пользователя, к которому уже
подоспел свежий колбэк), у `CONNECT` (и любого не-ASSIST типа) —
проявляется всегда, потому что переход к следующему вопросу происходит
автоматически, без паузы на новый рендер. Так как `M_ASC`-задачи
(`scripts/seedTP2.ts`) в `app/t-lesson/[t_lessonId]/page.tsx` **случайно**
конвертируются в `ASSIST` или `CONNECT` 50/50 — примерно половина
попыток по всему тренажёру (не только по пилотным тэгам) молча
записывала верный ответ как неверный.

Воспроизведено вживую (`npm run dev` + `/api/auth/test-login`,
локальный tabId управлялся напрямую через Browser pane): ответил
верно на `CONNECT`-вопрос, экран показал "Правильно 1 из 1", в БД
записалось `done_right=0, done_wrong=1`. Исправлено через `scoreRef`
(`useRef`, по тому же паттерну, что уже был у `isRightListRef` в этом
же файле) — обновляется синхронно вместе с `setScore` и читается в
`goToNextQuestion` вместо самого `score` state. После фикса тот же
сценарий даёт `done_right=1, done_wrong=0, done_right_percent=100`.
Старые (уже записанные до фикса) строки `t_lesson_progress` задним
числом не пересчитывались.

Заодно найден и исправлен **несвязанный** побочный баг, обнаруженный
при попытке проверить фикс: `components/TrainerMascot.tsx` статически
импортировал `lottie-react` (`import Lottie from "lottie-react"`) —
без `next/dynamic(..., {ssr:false})`, как уже сделано в этом же
`TQUIZ.tsx` для того же пакета. При холодном старте dev-сервера первый
SSR-рендер `/t-lesson/[id]` падал с `ReferenceError: document is not
defined` (стек вёл через `trainer-question.tsx` → `TrainerMascot.tsx`
→ `lottie-react`). Исправлено тем же `dynamic(..., {ssr:false})`.
Статические импорты `lottie-react` в других файлах (их много) не
трогались — за пределами конкретно этой SSR-цепочки они, по всей
видимости, не проявляют проблему, и это отдельная, более широкая
задача, если вообще стоит того.

Также отдельно замечен отладочный забытый код в `TQUIZ.tsx`:
`useState(questions1.slice(0, 1))` с комментарием "для тестирования Rive
сундука — только 1 вопрос" — из-за этого КАЖДЫЙ заход в любой урок
тренажёра был ограничен одним случайным вопросом вместо полного набора
задач урока. Убран при переделке карты скиллов ниже (понадобилось для
этапов — без полного набора вопросов сессии стейджи не имели смысла).

## Переделка карты скиллов тренажёра — этапы внутри темы (2026-08-27)

По итогам обсуждения с пользователем (см. историю диалога) исходную идею
"дерева скилов" со змейкой между темами заменили на другую модель:

- **Темы (t_lesson) друг от друга не зависят и открыты сразу** — ученик
  готовится не абстрактно "к физике", а к конкретным задачам экзамена, и
  должен уметь начать с любой темы (например, сразу с "Газ и нагрев",
  не проходя предварительно "Кинематику"/"Динамику"). Старая
  последовательная блокировка тем (`isDisabled` от процента предыдущей
  темы) убрана.
- **Внутри одной темы — этапы (1-4)**, открывающиеся последовательно по
  мере тренировки именно этой темы. Новое поле `t_challenges.stage`
  (int, default 1) — заполнено один раз через `NTILE(4) OVER (PARTITION
  BY lesson_id ORDER BY "order")`, прямым SQL (не куратором по смыслу
  сложности — это стартовая авто-разбивка, можно уточнить позже). У
  коротких уроков (мало задач) NTILE сам даёт меньше 4 групп — это и
  есть требуемое "от 1 до 4 этапов", без специальной обработки.
- **Переключатель класса** (9/10/11) вместо одновременного показа всех
  классов на одном экране — начальная идея показывать пирамидой все
  классы сразу была отвергнута пользователем как перегруженная и
  нерабочая на мобильном узком экране.
- Новый `t_courses.courseId` (FK на `courses`, nullable) — связь предмета
  тренажёра с основным курсом, чтобы `/trainer` в будущем мог сам
  открываться на нужном предмете по активному курсу юзера (сама
  автоматика выбора предмета по `courseId` — НЕ реализована в этой
  сессии, только связь в БД; сейчас проставлено вручную: `t_courses`
  id=21 "Ф10 ФИЗИКА-10" → `courses` id=12 "ЕГЭ Физика", id=1
  "М9 МАТЕМАТИКА-9" → id=11 "ЕГЭ Математика Профиль").

Новый компонент `components/trainer-grade-tree.tsx` (`TrainerGradeTree`)
заменил `TrainerSkillTree` внутри `tab-t-courses.tsx` (сам файл
`trainer-skill-tree.tsx` не удалён — не проверялось, не используется ли
где-то ещё, оставлен как есть). Вертикальный список карточек тем
(мобильная раскладка) вместо горизонтальной змейки; в каждой карточке —
ряд квадратов-этапов с иконками уровня мастерства из lucide-react (Egg
→ Shield → Sword → Crown, по кругу если этапов почему-то больше 4) и
бейджем-подарком (`Gift`) на последнем этапе, если он пройден. Порог
разблокировки следующего этапа — тот же `90%`, что уже использовался в
проекте для последовательной разблокировки уроков (`GetTLessonStat`),
для консистентности; новая функция `GetTLessonStageStat` в
`usefulFunctions.ts` — та же логика, но с фильтром по `stage`.

Проброс этапа в сам тренажёр: `/t-lesson/[id]?stage=N` →
`app/t-lesson/[t_lessonId]/page.tsx` фильтрует `t_lesson.t_challenges`
по `stage` ТОЛЬКО для списка "какие вопросы задавать" — пул дистракторов
для ASSIST/CONNECT типов (`other5Questions`/`otherQuestions`) намеренно
берётся из ВСЕХ вопросов темы, а не только этапа, чтобы у коротких
этапов всё равно было из чего собрать 5-6 непохожих неверных вариантов.
Без `?stage=` (старые ссылки, прямой заход без параметра) — поведение

## Баг тренажёра: визуальное "залипание" выбора варианта (2026-08-27)

Пользователь нашёл живьём: в ASSIST-вопросе кликаешь вариант 3, потом
вариант 1 (подсвечивается верно), потом быстро кликаешь вариант 5
несколько раз подряд — подсветка "выбрано" не переходит на него,
остаётся на варианте 1. Если после этого кликнуть вариант 4 (сработает
сразу), а затем снова вариант 5 — он тоже сработает.

Причина — `components/AnimatedOptionButton.tsx`: `getTransition()`
задаёт `delay: index * 0.08` на родительском объекте transition
(изначально — для каскадного появления кнопок при первом показе
вопроса: 6-й вариант появляется на 0.4с позже 1-го). Но `y`/`boxShadow`
(меняются при КАЖДОМ клике выбора, не только при монтировании — это и
есть подсветка "выбрано") у себя переопределяли только `duration`, не
`delay`, и поэтому наследовали тот же `index * 0.08` от родителя. Для
варианта 5 (index 4 из 6) это 0.32с задержки — при быстром повторном
клике на ЭТОТ ЖЕ вариант анимация просто не успевала стартовать до
следующего клика, который её заново перезапускал (visual answer вечно
"откладывается"). Сам выбор (React state) при этом регистрировался
верно всегда — баг был чисто в подсветке, не в логике ответа.
Исправлено — явный `delay: 0` для `y`/`boxShadow`, чтобы не наследовать
стаггер входной анимации. Воспроизведено и проверено на том же сценарии
(10 быстрых кликов подряд на вариант с index=4) — теперь подсвечивается
сразу.

## 4 новые фичи тренажёра: INSERT, SWIPE v2, MEMORY, HP-босс (2026-08-27)

По итогам обсуждения геймификации с пользователем ("основная задача —
приложение должно носить игровой, развлекательный, увлекающий
процесс") — сделаны все 4 фичи из списка, последовательно, каждая со
своим коммитом/деплоем/live-проверкой. Общий принцип (подтверждён
пользователем на примере уже существующих CONNECT/SWIPE): все новые
типы — **новый рендер существующих M_ASC-данных**, ни один не требует
новых полей БД или нового контента.

### INSERT — пропущенная буква в формуле

`lib/formulaLetters.ts` (`extractLetterCandidates`, `pickInsertBlank`)
— извлекает изолированные однобуквенные переменные из LaTeX-формулы
(`t_challengeOptions[0].text`): сначала вырезает `\command`-токены
(`/\\[a-zA-Zа-яА-Я]+/g` — попутно убирает и греческие команды типа
`\nu`/`\rho`, превращая их в обычное многобуквенное слово, которое уже
не проходит проверку изоляции), затем ищет буквы, не являющиеся частью
более длинного слова/индекса — поэтому кириллические индексы вроде
`_{тяж}`/`_{кин}` корректно НЕ считаются кандидатами. Одна случайная
буква вынимается и заменяется на `\boxed{\phantom{X}}` (KaTeX поддерживает
оба), обманки — реальные буквы из формул ДРУГИХ M_ASC-задач того же
урока. Graceful fallback на обычный ASSIST, если в формуле нет
подходящей буквы или в уроке не набирается 3 обманки-буквы.
`app/t-lesson/[t_lessonId]/type-insert.tsx` — рендер (4 кнопки-буквы,
переиспользует `AnimatedOptionButton`), двухшаговый флоу ответа
(выбор → "ответить") общий с ASSIST — проверки `questionType ===
'ASSIST'` в `trainer-question.tsx`/`TQUIZ.tsx` обобщены до
`isSelectThenSubmitType`, чтобы не дублировать transition-логику
(hearts/score/goToNextQuestion) под каждый новый тип с тем же флоу.

### SWIPE — переделан с нуля (дуэльная арена)

Пользователь явно попросил не трогать `type-swipe.tsx`/
`swipe-component.tsx` (они остались в репозитории, просто больше не
рендерятся), а сделать НОВЫЙ визуал с той же идеей (drag влево/вправо
между двумя вариантами). Новый `app/t-lesson/[t_lessonId]/swipe-arena.tsx`
+ `type-swipe-v2.tsx`: два поля-мишени слева/справа с формулой-вариантом
ВСЕГДА видны (не только во время драга), карточка вопроса перетаскивается
между ними и подсвечивает рамку ближайшего поля. Логика ответа (drag
threshold/velocity, `onAnswer('right'/'wrong')`) — та же, что уже
надёжно работала в оригинале, не переписывалась. Заодно SWIPE впервые
добавлен в случайный пул M_ASC-рендера (`ACStype` в page.tsx) — раньше
тип существовал только для настоящих БД-задач с `type='SWIPE'`,
которых в текущих курсах физики/математики нет, так что код был
фактически недостижим для тренажёра формул.

### MEMORY — найди пары (Concentration)

`app/t-lesson/[t_lessonId]/type-memory.tsx` — 8 перевёрнутых карточек
(4 пары: подпись переменной M_ASC-задачи ↔ её формула, текущая задача +
3 случайных других того же урока), клик на две подряд — совпало, обе
остаются открытыми (зелёная рамка+галка), не совпало — переворачиваются
обратно через ~700мс. Без штрафа сердечком за промах — это механика на
запоминание, не на проверку знания. Переиспользует уже существующий
контракт `onAllPairsMatched` (тот же, что был у CONNECT в
`trainer-question.tsx`) — `TQUIZ.tsx` вообще не пришлось трогать, MEMORY
просто ещё один "не select-then-submit" тип, как CONNECT/SWIPE.

### HP-босс на финальном (корона) этапе темы

Чисто визуальный слой, НЕ новая система жизней — существующие 3
сердечка игрока (`threeHearts` в TQUIZ.tsx) остаются единственным
условием проигрыша. `components/trainer-boss-bar.tsx` — HP-полоса
(`hp = 100 - (score/questions.length)*100`, то есть HP=0 ровно когда
все ответы верны — совпадает с уже существующим `isPerfectScore`/
сундуком) + красная вспышка на плейсхолдер-иконке (emoji 👹,
пользователь заменит на гифки персонажа/босса позже) при каждом верном
ответе. `trainer-grade-tree.tsx` уже точно знает, какой этап темы
последний (`idx === stages.length - 1`) — приписывает `?boss=1` к
ссылке на него; `page.tsx` читает параметр и пробрасывает `isBossStage`
через `TQuiz` → `TrainerQuestion` (тот же паттерн, что раньше был у
мёртвого `?stage=`, без изменений схемы БД).

Все 4 фичи проверены вживую (`npm run dev` + `/api/auth/test-login`,
`/t-lesson/14` и `/t-lesson/14?boss=1`) через Browser pane: рендер
каждого типа, корректный подсчёт верно/неверно в финальной статистике
урока, отсутствие ошибок в серверных логах. Не сделано (следующие

## Баг тренажёра: onMouseDown-setState глушил реальный click (2026-08-27)

Пользователь поймал живьём то, что выглядело как рецидив уже
исправленного ранее в этой же сессии бага "залипания выбора" (см. выше
«Баг тренажёра: визуальное "залипание" выбора варианта»): в ASSIST
клик на конкретный вариант ответа не выбирается, а после кликов на
соседние иногда вдруг срабатывает. Но в этот раз баг воспроизводился и
на ОДИНОЧНОМ клике, не только при быстрых повторных — значит причина
другая, не connected к анимационному delay, который чинили в тот раз.

Диагностика: залогировал `mousedown`/`click` на уровне `document`
(capture-фаза) перед реальным кликом через Browser pane. Оказалось:
браузер диспатчил `mousedown` (`isTrusted: true`), но `click` до React
НИКОГДА не долетал. При этом синтетический `el.click()` из консоли на
ТОМ ЖЕ элементе срабатывал мгновенно — из-за этого при отладке в прошлый
раз (когда воспроизводили баг через JS/скрипты, а не реальные клики)
проблема не была замечена.

Причина — `onMouseDown={() => setIsPressed(true)}` в
`components/AnimatedOptionButton.tsx` (и идентичный паттерн в
`ConnectItem`, `app/t-lesson/[t_lessonId]/type-connect.tsx`): `setState`
внутри нативного обработчика `mousedown` вызывает React-рендер МЕЖДУ
реальными браузерными `mousedown` и `mouseup` этого же жеста — из-за
этого браузер иногда не формирует итоговый `click`-event на элементе
(смена DOM/пропсов framer-motion `motion.button` посреди уже начатого
жеста нарушает его внутреннее отслеживание указателя). Исправлено в
обоих компонентах: убраны `isPressed` state и
`onMouseDown`/`onMouseUp`/`onMouseLeave` целиком, "прожатый" визуал
(`y: 2`, уменьшенная тень) теперь через встроенный `whileTap`
framer-motion — не требует state/обработчиков мыши и не мешает
нативному click. Заодно в `ConnectItem` добавлен явный `delay: 0` для
`y`/`boxShadow` (тот же паттерн, что уже был в `AnimatedOptionButton`,
на случай похожей на прошлый раз проблемы с быстрыми повторными
кликами).

Проверено вживую РЕАЛЬНЫМИ кликами через Browser pane (не через
`el.click()` из консоли — это принципиально, именно так баг маскируется):
5 последовательных кликов на разные/повторные варианты ASSIST — каждый
сработал с первого клика; CONNECT — 3 пары угаданы кликами с первого
раза каждая. **Вывод на будущее**: при отладке "клик не срабатывает" в
любом framer-motion `motion.button`/`motion.div` с `onClick` — сразу
проверять, нет ли рядом `onMouseDown`/`onMouseUp`, вызывающего
`setState`; для "нажатого" визуального состояния всегда использовать
`whileTap`, а не ручные обработчики мыши. Синтетический `el.click()` в
консоли/автотестах НЕ воспроизводит этот класс багов — нужен именно
реальный `mousedown`→`mouseup` через Browser pane/`computer`-тул.

## INSERT: почему был редкий, разбор слитных букв, двойной пропуск, новый визуал (2026-08-28)

Пользователь заметил, что тип INSERT выпадает подозрительно редко.
Прогнал `pickInsertBlank` по всем 137 M_ASC-задачам тренажёра — INSERT
был технически возможен только для 36.5% из них, а с учётом случайного
выбора типа (1 из 5) реально показывался примерно в 7% случаев.

**Причина — не осознанное ограничение, а баг в `lib/formulaLetters.ts`.**
`extractLetterCandidates` считала кандидатом только ИЗОЛИРОВАННУЮ букву
(не соприкасающуюся с другой буквой). А в физике переменные почти всегда
пишутся слитно, без знака умножения: `mgh`, `qvB`, `CU^2`, `PV=νRT` — тут
`m`,`g`,`h` три РАЗНЫЕ переменные, но раз они стоят вплотную, регекс не
считал кандидатом ни одну из них. Это задевало 24 из 68 "провальных"
формул не по теме Виета (там формул вообще нет, id=1,2,3 — просто пары
чисел на подбор корней, не в счёт).

Переписано `findLetterOccurrences` — слитную латиницу (`mgh`) теперь
считаем произведением однобуквенных переменных и раскладываем на
отдельные кандидаты, КРОМЕ известных названий функций, которые в этих
формулах пишутся обычным текстом без backslash (`sin`, `cos`, `tg` и
т.п. — список `FUNCTION_WORDS`). Кириллица слитно (2+ буквы) по-прежнему
НЕ разбивается — это словесные подстрочные индексы (`тяж`, `кин`,
`красн`), не переменные; изолированная одна кириллическая буква — как и
раньше, валидный кандидат. Отдельно найден и исправлен баг в первой
версии этого фикса: `(?<!\\)[A-Za-z]+` как lookbehind на весь
квантификатор отбрасывает только ПЕРВУЮ букву команды, если её
предваряет backslash (для `\huge` регэксп сдвигается на 1 символ и ловит
"uge" как кандидатов) — переписано на матч без lookbehind + проверку
`latex[match.index - 1] === '\\'` после матча, отбрасывающую весь кусок
целиком. После фикса — 78/137 (56.9%) формул дают хоть какой-то INSERT;
остаток — легитимный лимит (в уроках с 2-4 задачами не набирается даже 3
разные буквы-обманки среди соседей, тут дело не в извлечении букв).

**Двойной пропуск (усложнённый режим).** Пользователь попросил уметь
пропускать сразу 2 буквы, заполняемые по очереди, и явно уточнил: раз
умножение коммутативно, `mgh` и `hgm` (или любая перестановка) должны
засчитываться одинаково верными. Поэтому `pickInsertBlank(challenge,
siblings, wantDouble)` при `wantDouble=true` берёт ОБЕ загаданные буквы
**из одного и того же слитного произведения** (одного `runKey` в
`findLetterOccurrences`) — только тогда перестановка гарантированно не
меняет физического смысла формулы; буквы из разных, не связанных друг с
другом частей формулы для двойного режима не комбинируются (там порядок
в общем случае важен). Без подходящего произведения из ≥2 букв или без 3
обманок — тихо откатывается на однобуквенный режим (не на ASSIST).
`page.tsx` запрашивает `wantDouble` с вероятностью 40% на каждую
INSERT-задачу.

Проверка ответа — без учёта того, в какой конкретно из двух пропусков
какая буква попала: `correctAnswer` в `page.tsx` — это
`[...correctLetters].sort().join(',')`, и `type-insert.tsx` при
заполнении обоих пропусков отправляет наверх `onOptionSelected` с ТЕМ ЖЕ
преобразованием (`[...filled].sort().join(',')`) — обычное `answer ===
correctAnswer` в `TQUIZ.tsx` благодаря этому само становится
нечувствительным к порядку, без единой правки в `TQUIZ.tsx`. Для
однобуквенного режима формат не меняется (join одного элемента = он сам).

Первая версия требовала 4 обманки на двойной режим (было 3 на
одиночный) — из-за этого в маленьких уроках (3-4 M_ASC-задачи, обычный
размер одного "этапа" тренажёра) обманок никогда не хватало, и
усложнённый режим на практике НИКОГДА не срабатывал (проверено принудительным
`wantDouble=true` на реальных данных темы "Электродинамика" — все 3
попытки тихо откатывались на одиночный пропуск). Снижено обратно до 3 —
после этого двойной режим стабильно срабатывает там, где формула это
позволяет (например, `CU^2/2` → пропуск и C, и U).

**Новый визуал пропуска.** Пользователь отдельно попросил не рисовать
скучную "ячейку", а что-то, что подсказывает "сюда нужно вписать букву"
и красиво превращается в саму букву, другим цветом, чтобы не сливалось с
формулой. Вместо старого `\boxed{\phantom{X}}` (невидимый спейсер) —
`\underline{\color{ЦВЕТ}{ГЛИФ}}` прямо внутри LaTeX-строки формулы (без
разбиения на отдельные React-компоненты — `\color` в KaTeX работает "из
коробки", без `trust`). До ответа — глиф `?`, после клика по букве —
сама буква; заполненный/активный пропуск подчёркнут синим (`#4A90D9`,
уже использовался как цвет "текущий выбор" у SCROLL/слайдера), НЕ ещё
активный (второй пропуск, пока не заполнен первый) — приглушённым
серо-синим (`#5C6B73`), после проверки ответа — зелёным/красным
(`#A1D151`/`#DC605B`, как везде в приложении). Позиции пропусков внутри
`blankedFormula` помечены разными маркерами (`\boxed{\phantom{1}}`,
`\boxed{\phantom{2}}`) — не только для точечной подстановки, а и чтобы
на UI знать, какой из двух подсвечивать активным.

Клик по уже заполненной кнопке-букве снимает её с пропуска (простой
"отменить выбор", пропуск снова становится активным) — без этого
опечатка в первом пропуске была бы неисправима до конца попытки.

Прямое расширение `QuestionType` (`page.tsx`): `insertCorrectLetters?:
string[]` — 1 или 2 буквы, в порядке пропусков слева направо; отдельно
от `correctAnswer` (который для проверки, а не для UI-подсветки
конкретных кнопок).

**Живая проверка** (`npm run dev` + `/api/auth/test-login`,
`/t-lesson/6` и `/t-lesson/22`, оба типа выпадают случайно — гонялся,
пока не поймал; под конец на короткое время принудительно
захардкоживал `randomASCtype`/`wantDoubleBlank` прямо в `page.tsx`,

## Баг админки /admin/t-challenges: форма "Добавить задачу" схлопывалась в 24px (2026-08-28)

Пользователь сообщил: при выборе (в т.ч. только что добавленного) этапа
форма добавления задачи внизу становится "маленького по вертикали
размера", а текст внутри — большой и обрезается пополам, непонятно что
написано.

Причина — НЕ в самом добавлении этапа, а в классической ловушке
flexbox: `app/admin/t-challenges/structure-browser.tsx`, панель 4
(`<div className="flex-1 ... overflow-y-auto flex flex-col gap-4">`)
содержит сверху `UnitChallengePool` (список ВСЕХ задач юнита,
сгруппированных по этапам — при заполненном юните это десятки строк,
высота ничем не ограничена) и НИЖЕ, если выбран урок — блок "Добавить
задачу" на `flex-1 min-h-0`. Когда родитель сам `overflow-y-auto`
(скроллится, то есть у него нет верхней границы для контента), у
"оставшегося места" для соседнего `flex-1`-блока нет стабильного
значения: пул уже занимает больше, чем видимая высота панели, свободного
места 0 или отрицательное, и `min-h-0` явно РАЗРЕШАЕТ дочернему
элементу схлопнуться до нескольких пикселей вместо естественной высоты
контента — internal `overflow-y-auto` формы при такой высоте контейнера
показывает только полоску текста, отсюда "текст обрезан пополам". Баг
усиливается с ростом количества задач в юните (чем больше пул — тем
меньше "остатка" форме) — поэтому пользователь заметил его именно на
занятых юнитах вроде "Динамика" (16 задач в пуле).

[45vh] overflow-y-auto">` (сам блок пула, не заголовок над ним) — у пула
теперь СВОЯ явная граница высоты и свой скролл, вместо неограниченного
роста внутри общей `overflow-y-auto` панели. После этого "остаток"
пространства для формы ниже вычисляется нормально, её `flex-1 min-h-0`
получает разумную высоту, и обе внутренние `overflow-y-auto` области
(форма слева, превью+список справа) скроллятся каждая в разумных
пределах, а не схлопываются.

Диагностика заняла время из-за постороннего шума в самом инструменте
отладки: `getBoundingClientRect()`/`window.innerWidth` через
`javascript_tool` в Browser pane периодически возвращали 0 (иногда сразу
после смены размера окна тулом `resize_window`, иногда без видимой

размеры) при внешне нормальном скриншоте — не доверять им и не тратить
время на "починку" несуществующего бага; переключаться на визуальную
проверку (`computer screenshot` + `read_page`/`find`/`scroll_to` по
ref'ам, которые в этой ситуации остаются достоверными) вместо DOM-

## Баг змейки карты скиллов при неполном ряду (5/6 этапов) (2026-08-28)

Пользователь поймал баг в самой змейке (см. выше "Переделка карты
скиллов тренажёра"): при 5 этапах 5-й рисовался под 1-ым вместо 4-ого; а
когда добавили 6-ой — 5-й вставал на место (под 4-ым), а 6-ой снова
рисовался под 1-ым вместо 3-тьего.

Причина — прошлая реализация ряда была обычным flex-рядом: боксы
(`flex-shrink-0`, фикс. ширина) и соединительные линии между ними
(`flex-1`, растягиваются). Для ПОЛНОГО ряда (4 этапа) это работало
идеально — 4 бокса+3 линии равномерно растягивали ряд на всю ширину
карточки. Но для НЕПОЛНОГО последнего ряда (змейка развёрнута справа
налево, а этапов в нём меньше 4) в ряду физически МЕНЬШЕ элементов —
flex просто сжимал их и растягивал единственную имеющуюся линию на всю
ширину карточки, из-за чего блок "бокс+линия+бокс" целиком уезжал к
одному краю (левому, т.к. первый DOM-элемент ряда всегда прижат влево),
а не занимал СВОИ настоящие колонки.

Исправлено переходом с flex на CSS grid с ФИКСИРОВАННЫМИ колонками:
`gridTemplateColumns: "36px 1fr 36px 1fr 36px 1fr 36px"` (7 треков —
бокс,щель,бокс,щель,бокс,щель,бокс — под COLUMNS_PER_ROW=4 колонки
боксов). Каждый этап получает АБСОЛЮТНЫЙ трек по формуле `boxColumn(j)
= (isReversed ? COLUMNS_PER_ROW-1-j : j)*2+1`, где `j` — порядковый
номер внутри ряда (0-индекс), а НЕ по количеству элементов, реально
присутствующих в ряду — поэтому одинокий 5-й этап в развёрнутом ряду
сразу получает трек 7 (правый край, под 4-ым), а не подстраивается под
то, сколько соседей у него в ряду. Недостающие колонки (в неполном
ряду) — просто пустые ячейки грида, не занятые ничем, не стягивающие на
себя соседей. Линия между соседними по ПОРЯДКУ (не по колонке) этапами

боксами, независимо от направления змейки.

## Ещё один баг змейки: 5-й и 6-й этап стояли ДРУГ ПОД ДРУГОМ (2026-08-28)

Пользователь поймал сразу после предыдущего фикса, на реальных 6
этапах "Динамика": линия между 5-ым и 6-ым этапом шла не из центра
5-ого, а с его НИЖНЕГО края, и заходила не в центр 6-ого, а в его
ВЕРХНИЙ край. Плюс отдельная жалоба — соединитель между 4-ым и 5-ым
(вертикальный, между рядами) слишком короткий.

Первая жалоба — на самом деле куда серьёзнее, чем просто "не из
центра": 5-й и 6-й этап физически стояли ОДИН НАД ДРУГИМ, а не рядом.
Причина — CSS Grid auto-placement. У боксов/линий был явно задан только
`gridColumn` (без `gridRow`) — а в развёрнутом (змейкой) ряду они идут
в DOM в порядке УБЫВАНИЯ колонки (трек 7, затем 6, затем 5, ...).
Дефолтный (`sparse`) алгоритм авторазмещения Grid двигает "курсор"
только ВПЕРЁД (по возрастанию колонки) и никогда не возвращается назад
в рамках одной авто-строки — если следующий элемент просит колонку
МЕНЬШЕ, чем курсор уже прошёл, браузер молча переносит его в СЛЕДУЮЩУЮ
авто-строку. Из-за этого каждый элемент развёрнутого ряда с 3+ детьми
попадал в свою отдельную "невидимую" auto-row (проверено измерением:
высота грид-контейнера ряда была 74px = два бокса по 36px + линия,
вместо ожидаемых 36px) — визуально это давало ровно описанный симптом:
верхний бокс кончается снизу, линия — тонкая полоска сразу под ним,
следующий бокс начинается сразу под линией.

Исправлено — явный `gridRow: 1` на КАЖДОМ элементе ряда (и боксах, и
линиях), что убирает любую зависимость от порядка DOM/колонок при
авторазмещении: все элементы одного ряда гарантированно на одной
строке грида, независимо от направления змейки.

Соединитель между рядами (`w-0.5 h-3` → `h-6`) заодно удлинён вдвое по
отдельной просьбе — чисто эстетическая правка, не связанная с
grid-багом выше.

Проверено вживую (`npm run dev`, `/api/auth/test-login`, `/trainer`,
реальные 6 этапов "Динамика", сверено `getBoundingClientRect()` каждого
бокса/линии, не на глаз): высота грид-контейнера обоих рядов ровно

### Явный выбор рендер-стиля для M_ASC-подобных задач (ASSIST/CONNECT/
### SWIPE/INSERT/SCROLL как настоящие сохраняемые типы)

До этого разговора INSERT/SCROLL были ЧИСТО рендер-выбором на лету — в
`page.tsx` любая задача с `type='M_ASC'` случайно (равновероятно 1 из 5)

`INSERT`/`SCROLL` напрямую, и такая задача ВСЕГДА рендерилась бы именно

1. **Postgres-enum расширен** — `ALTER TYPE "type" ADD VALUE 'INSERT'`

   одно физическое имя `"type"` в Postgres (используются и `challenges`
   курсов, и `t_challenges` тренажёра), поэтому правка одна на оба.
2. **`page.tsx`**: вместо `if (t_challenge.type === 'M_ASC')` — новая
   функция `isMAscLike(type)` = `type === 'M_ASC' || ACStype.includes(type)`
   (где `ACStype = ['ASSIST','CONNECT','INSERT','SWIPE','SCROLL']`).
   Внутри — `randomASCtype` теперь: для `M_ASC` как раньше случайный
   выбор, для ПРЯМОГО типа (уже равного одному из ACStype) — этот же
   тип напрямую, без рандома. Все 5 мест, где код ищет

## SCROLL: горизонтальный скролл страницы, смещение бегунка, анимация (2026-08-28)

Три жалобы на визуал типа SCROLL (`type-scroll.tsx`), первые две по сути
одна и та же причина.

**Горизонтальный скролл страницы + бегунок не под крайним вариантом.**
Подписи вариантов стояли ровно на `0%/50%/100%` контейнера с
`-translate-x-1/2` (центрирование НА этой точке). Для крайних вариантов
это означало, что половина ширины подписи вылезала ЗА пределы
контейнера (у левой — в отрицательный `x`, у правой — за правый край) —
собственно и есть источник горизонтального скролла страницы. Одновременно
сам бегунок Radix Slider (`size-6` = 24px) держит СВОЙ центр не в
диапазоне `[0%, 100%]`, а `[радиус, 100% - радиус]` = `[12px, 100% -
12px]` — иначе кружок вылезал бы за трек в крайних положениях. Из-за
этого расхождения (подписи на 0/100%, бегунок на 12px/100%-12px) они не
совпадали по вертикали в крайних позициях.

Оба фикса объединены: подписи теперь стоят на ТЕХ ЖЕ точках, что и центр
бегунка (`TICK_POSITIONS = ['12px', '50%', 'calc(100% - 12px)']` —
константа `THUMB_RADIUS_PX = 12`, ровно половина `size-6`) — это разом
чинит и совпадение по вертикали (запрошено явно), и уменьшает вылет за
край (запрошено косвенно, через "не влезли/появился скролл"). Плюс сами
подписи уменьшены (`max-w-[92px]`, `text-xs` вместо `text-base`,
`break-words` вместо `whitespace-nowrap`) — длинные формулы переносятся
на 2 строки вместо того, чтобы распирать контейнер по горизонтали.

Проверено вживую (`npm run dev`, временный хардкод `randomASCtype =
'SCROLL'` в `page.tsx` для гарантированного попадания, потом убран) —
десктоп (1280px) и мобильная ширина (375px): `document.documentElement.
scrollWidth === clientWidth` (без переполнения) на обеих; координаты
центра бегунка (`getBoundingClientRect`) сверены с координатами центра
каждой из 3 подписей — совпадение день-в-день (412/636/860px) во всех
трёх положениях.

**Анимация бегунка и подписей.** Раньше позиция бегунка (Radix задаёт
её через inline-стиль) менялась мгновенно, без перехода; подписи меняли
цвет через обычный CSS `transition-colors` без явной длительности.
Добавлено:
- `SliderThumb`/`SliderRange` — `transition-all duration-300 ease-in-out`
  (проверено `getComputedStyle`: `transitionProperty: all,
  transitionDuration: 0.3s, transitionTimingFunction:
  cubic-bezier(0.4, 0, 0.2, 1)` — это и есть кривая с разгоном и
  торможением, которую просил пользователь). Позиция бегунка в Radix
  выставляется через inline `style`, поэтому обычный CSS-переход на
  элементе исправно её подхватывает — переписывать перетаскивание на
  `motion.div` не потребовалось (сломало бы клавиатурную/drag-логику
  Radix без явной необходимости).
- Подписи вариантов — обёрнуты в `motion.div` (framer-motion),
  `animate={{backgroundColor, borderColor, color, scale}}` с тем же
  `transition={{duration: 0.3, ease: [0.4,0,0.2,1]}}` — карточка
  выбранного варианта плавно "зажигается" (цвет + лёгкое увеличение
  масштаба), невыбранного — плавно "тухнет", вместо мгновенной смены
  цвета.

Живьём подтверждено: выбор ответа и последующая проверка (кнопка
"ответить") корректно перекрашивают верный вариант в зелёный, неверный
выбранный — в красный (через `getComputedStyle` на `backgroundColor`/
`borderColor` после нажатия) — цветовая логика не пострадала от
перехода на `motion.div`.

`npx tsc --noEmit` чист.

Заодно обнаружено (не баг кода, особенность инструментария): значения
`useMotionValueEvent`/inline-`style`-снимки framer-motion, прочитанные
через `javascript_exec` сразу после клика/навигации без явного
`wait`, иногда попадают "между кадрами" — показывают состояние ДО начала
только что запущенного 300мс-перехода. Один такой снимок в этой сессии
ошибочно выглядел как "бегунок не сдвинулся" — при повторном чтении
после `wait` оказался корректным финальным состоянием. Также подтверждён
отдельный, чисто инструментальный артефакт: прерванный (`left_click_drag`)
жест в предыдущей фазе этой же сессии оставил синтетический курсор в
состоянии "зажатой кнопки", из-за чего JS-driven `location.reload()`
показывал карточку SWIPE смещённой на `x≈138px` без всякого
взаимодействия — настоящая браузерная навигация (`navigate`, не
`location.reload()` изнутри страницы) полностью сбрасывает это
состояние.

## Пилот content-generation: словарный слой для тренажёра (2026-08-28)

По итогам обсуждения масштабирования контента ("нужно добавить вопросы
про единицы измерения/термины, но их комбинаторно много — как это
сделать лучше?") — пользователь сам сформулировал ключевую идею: раз
для генерации любого M_ASC-вопроса достаточно пары "вопрос+правильный
ответ", проблема НЕ комбинаторная — можно писать вопросы про величины
(символ формулы) программно, из небольшой таблицы метаданных, а не
вручную на каждую пару "формула×тип вопроса". Согласованная структура:
лессоны по 2-3 формулы за раз ("в первом лессоне все вариации про F
тяжести и F упругости"), периодически лессон-контрольная с миксом уже
пройденных формул + мини-босс (уже был готов заранее — см. "Мини-босс
обобщён..." выше), от простого к сложному.

**Реализовано как пилот на 3 новых урока** темы "Динамика" (`t_unit`
id=4), `scripts/seedDynamicsVocabPilot.ts` — параметризуемый генератор
(не одноразовый хардкод): на вход список `Quantity{symbol, name, unit}`,
на выход для каждой величины — "Что такое $symbol$?" (→ name) и "В чём
измеряется $symbol$?" (→ unit), плюс ОДИН обратный вопрос "Что
измеряется в $unit$?" на каждую РАЗЛИЧНУЮ единицу измерения в наборе
(склейка нескольких названий через `|`, если единица неоднозначна —
конвенция multi-correct, см. выше). Существующие formula-recall
challenges (уже в БД) не трогаются — дублируются (не переносятся) в
новый урок тем же способом, что и `POST
/api/admin/t-challenges/[id]/duplicate`.

Лессон 1 "Термины: сила тяжести и упругости" (id=39) — дубли F_тяж=mg
и F_упр=kΔx + 4 словарных вопроса + 1 обратный ("Что измеряется в Н?"
→ "сила тяжести|сила упругости"). Лессон 2 "Термины: сила Архимеда и
давление" (id=40) — дубли F_Арх, давление тела (P=F/S), давление
жидкости (P=ρgh) + словарь (P — ОДНА величина "давление" на обе formulas,
не задвоена). Лессон 3 "Контрольная 1" (id=41, `isReviewStage` по слову
"контрольная" в названии → автоматически мини-босс) — чистый повтор всех
5 формул выше, без словаря. Заодно удалены 2 мусорных тестовых урока
("урок 5"/"уроооок 6" с "3+3"/"1+1", наследие отладки бага змейки карты
скиллов в более ранней фазе сессии).

**Два реальных бага в рендер-пайплайне вскрылись именно из-за смешения
жанров вопросов в одном уроке** (раньше урок всегда был только формулами
— однородный жанр, оба класса багов были невидимы):

1. **Обманки могли быть чужого жанра.** Пул кандидатов в дистракторы
   (`other5Questions`/`otherQuestionsForSwipe`/`otherQuestionsForScroll`/
   `otherQuestions` в `page.tsx`, 4 места) фильтровался только по
   "не совпадает текстом с правильным ответом" — для словарного вопроса
   "Что такое $F_{упр}$?" (ответ "сила упругости", обычный текст) в пул
   вполне мог попасть сосед-ФОРМУЛА ("$kΔx$", LaTeX) как вариант ответа.
   Это тот же класс проблемы, что уже чинили для числовых дистракторов
   (единственный непохожий вариант угадывается без решения) — только
   тут "непохожесть" визуальная (LaTeX-формула среди обычного текста),
   а не числовая. Исправлено эвристикой `looksLikeFormula(text) =
   text.includes('$')` + `sameAnswerGenre()` — пул обманок теперь
   ограничен вопросами ТОГО ЖЕ жанра (все-формулы или все-текст).
   Существующие (чисто формульные) уроки не затронуты — эвристика для
   них всегда true===true, ведёт себя как раньше.
2. **Одинаковый текст ответа у двух РАЗНЫХ challenges мог попасть в один
   пул дважды.** Обратный вопрос "Что измеряется в Н?" хранит несколько
   `t_challengeOptions` (по одной на каждое верное название, см. ниже) —
   его канонический `[0].text` оказывается равен "сила тяжести", ТОЧНО
   ТАК ЖЕ как у отдельного вопроса "Что такое $F_{тяж}$?". Оба — РАЗНЫЕ
   challenges с одинаковым текстом ответа, и оба проходили фильтр "не
   равно ответу ТЕКУЩЕГО вопроса" независимо — пользователь мог увидеть
   "сила тяжести" ДВАЖДЫ в списке из 4 кнопок-вариантов. Исправлено
   `dedupeByAnswerText()` — после сборки пула кандидатов остаётся не
   более одного challenge на уникальный текст ответа. Общая защита в
   пайплайне рендера, не патч под конкретный урок — актуальна для
   любого будущего контента, где два разных challenge могут случайно
   иметь одинаковый ответ.

**Важный урок про сам формат хранения multi-correct**: изначальная
версия скрипта была БАГОВАННОЙ — обратный вопрос вставлял ОДНУ строку
`t_challengeOptions` с уже склеенным через `|` текстом
("сила тяжести|сила упругости"). Раз `t_challengeOptions[0].text`
используется рендер-пайплайном и как отображаемый текст КНОПКИ
(в том числе как текст-обманка у СОСЕДНИХ вопросов) — пользователь
увидел бы сырую строку с `|` прямо на кнопке ответа. Правильная
конвенция (как и задумано в `getCorrectAnswerText()`/комментарии в
`page.tsx` "показывается только ОДНА (каноничная, [0])") — НЕСКОЛЬКО
отдельных строк `t_challengeOptions`, каждая с `correct=true` и ЧИСТЫМ
(несклеенным) текстом; склейка через `|` происходит только один раз,
на чтении, внутри `getCorrectAnswerText()`. Пойман и исправлен ДО
деплоя — живой проверкой в Browser pane (увидел сырой "a|b" на кнопке),
не по обзору кода.

Живая проверка (`npm run dev`, реальные клики через Browser pane):

## Пилот: перестановка в начало темы + сортировка "термин → формула" (2026-08-28)

Сразу после пилота выше пользователь посмотрел на живой `/trainer` и не
